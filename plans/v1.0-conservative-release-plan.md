### T2 E2E 回归 CI（第一优先，CHANGELOG 已承诺但现状缺失）

**现状**：`frontend/e2e/` 下有 14 个 spec（a11y/admin/ai/alerts/auth/cases/dashboard/i18n/marketplace/playbooks/reports/security/threat-intel/verify），本地可跑（`npm run test:e2e`），但 `.github/workflows/` 里 5 个 workflow（ci-cd / pr-review-checks / release / security-audit / security-gate）**没有任何 E2E 步骤**。CHANGELOG 0.9.4 写过 "Cases E2E with CI trigger workflow"，该承诺在 9/20-21 CI 重组时丢失。

**步骤**：
1. 先读 `frontend/playwright.config.ts`，确认 spec 依赖的运行时（是否需要完整后端+DB，还是部分 spec 纯前端）；
2. 新增 `.github/workflows/e2e.yml`：
   - **PR required job**：只跑核心链路 4 个 spec——`auth/login.spec.ts`、`alerts/alert.spec.ts`、`cases/cases.spec.ts`、`dashboard/dashboard.spec.ts`（chromium 单浏览器，走 `--grep` 或路径过滤）；所需后端栈按 playwright.config 的要求用 services（postgres + redis）+ 后端容器起；
   - **nightly job**（`schedule: cron`）：全量 14 spec + a11y（`--workers=1`）；
3. 本地先跑通这 4 个 spec 再提 CI；CI 里注意登录测试对 admin 初始密码的处理（查 `e2e/utils/` 与 `global.setup.ts` 现有约定，不要硬编码新密码）；
4. nightly 连续绿两次后（可人工观察 1–2 晚），在 PR checks 里将 4-spec job 标 required（`.github/branch-protection` 由用户在仓库设置里操作，计划里只交付 workflow）。

**验收**：PR 上能看到 E2E job 且 4 核心 spec 绿；nightly 全量 job 存在且有 schedule 触发；workflow 语法通过 `actionlint` 或至少 YAML 解析。

**注意**：如 4 个核心 spec 在 CI 环境因环境差异失败，修复 spec 或环境的成本计入本任务（这正是 1–1.5 天预算的来源），**不允许跳过失败的 spec**。

## 4. 风险与回滚

- **T2 是最大不确定项**：E2E 在 CI 环境跑不通的调试成本可能超预算；超 2 天仍未绿时，降级方案为 nightly-only + 人工跑 4 核心 spec 留证据，向用户汇报后决断，不无限投入。
- **T3 可能暴露 worker 设计缺陷**：若问题超出"修 bug"范围（需重构通知管线），登记为 blocker 向用户汇报，不擅自扩大改动面。
- 所有提交按任务分批，单任务单（或少量）提交，出问题按提交回滚；`release/v1.0.0` 分支全程不 force-push。
